## 3. Can the current DB rebuild a faithful decision log?

There are two cases. **A**: the event has a journal for its whole life (created on schema v4 or later, i.e. after 2026-10-27, and never snapshot-restored or imported). **B**: everything else, which has only the end state, sometimes with a partial journal.

### What is lost or ambiguous, item by item

1. **Order of decisions.**
   - Case A: exact, from `action_id` / `change_id`.
   - Case B (no journal: events before 2026-10-27, deleted-then-imported events, and anything before a snapshot restore): only partial orders survive.
     - `race_id` order gives the global race order (AUTOINCREMENT).
     - `heat_id` order gives the round order.
     - `boat_event_id` orders the entries among themselves.
     - These sequences cannot be compared with each other. So **when a late entry was entered** relative to races is lost. It can be bounded: a boat first seen in a round-k heat was entered and assigned after round k was created and before her heat's first race (the app refuses joining a raced heat).
     - **When a correction or protest happened relative to `roundCreated` is lost.** This matters: a race-office correction before the next round changes that round, and one after it does not. The only check available is to replay and compare with the stored Heat_Boat.
     - Removed boats, recreated heats, undone races and redistributions, and transfers leave no trace.

2. **Who decided a DSQ, DNE, DGM, DPI or RDG.**
   - Not recorded anywhere.
   - Proxy:
     - Status entered on the original sheet (`submitHeatRaceScoresAtomic`): race office, so `raceScored` with `code`.
     - Status set on the leaderboard (`saveLeaderboardRaceResultsAtomic`): the app _assumes_ the protest committee (scoreStatus.ts:69-74), so `protestDecided`. A race-office DSQ (for example an OCS rescored) or an umpire's DSQ entered there is mislabelled.
   - Case B: a RaceAssignmentSnapshots row for (race, boat) tells you a protest-coded leaderboard edit happened to that race. Its absence proves nothing: a later correction un-shields. Snapshot rows written before the `frozen_position` / `frozen_status` columns existed hold only the order (raceAssignmentSnapshot.ts:49-58).
   - A change **from** a protest code back to a place: the app treats it as a correction (it un-shields). It could equally be a `protestDecided{cleared}` (reopening) or a `raceCorrected`. Ambiguous.

3. **Corrections against original sheets.**
   - Case A: the channel separates them.
   - Within one leaderboard save, though, the per-cell `edited` flag the renderer sends is **not stored**. From the net row diff you cannot always tell a boat the officer edited from a boat that merely moved up (A6.1 ripple after a DSQ). The rule: a status change to a protest code means protest; another status change means correction; a place change with an unchanged status is ambiguous between ripple and correction.
   - One save can mix several races and both kinds.
   - Case B: only the final state is left. The original sheet is lost, except for races with a snapshot: the frozen rows give the order before the first protest, for boats not un-shielded since.

4. **Finishing order against place numbers.**
   - The app receives typed **place numbers** (ScH:43-55). Boats not typed default to DNS (`seedRaceWithDefaultDnsScores`).
   - `applyRaceTieScoring` (raceScoring.ts:336-; shared/raceTieScoring.ts:32-77) rewrites FINISHED positions to the start place of their group. So the stored positions _are_ an order with ties: typed `1,1,3` and `1,1,2` both store `1,1,3`. Typed gaps are compacted away, which the library cannot represent anyway.
   - The positions of ZFP/SCP/T1 rows are not rewritten. They keep the typed place, gaps included, but sorting still gives the order.
   - Non-finishers all get `largestHeat + 1`, so their relative order is lost. This is harmless: the library order of coded lines does not matter.
   - **After a protest or correction**, `scoreRaceColumn` rewrites the other boats' positions (A6.1 promotion), so the stored order is the post-decision order. To build `raceScored` with the DSQ'd boat in her original slot you need the journal's `old_row`s or the snapshot.
   - Kept places of RDG/DPI boats: `held_place` exists only since v8 (2026-11-05). Before that, `position` holds points and the place is lost (journal or snapshot only).

5. **DPI or RDG on the original sheet.** The app accepts any status on `submitHeatRaceScoresAtomic` (penaltyStatuses includes DPI; rdgStatuses are allowed; scoreStatus.ts:82-86). The library's `RaceLine.code` cannot hold DPI or RDG; they exist only as `protestDecided`. Rebuilding needs `raceScored` with _some_ line for that boat, then a `protestDecided`. Her actual finishing place, if any, is unknown, so the line has to be invented. That conflicts with the "no derived values as data" principle: flag it, do not guess.

6. **Ties.**
   - Equal stored positions among FINISHED and penalty boats mean `tied`. Recoverable.
   - Exception: before v8, a tie partner of a boat given RDG or DPI was re-scored as finishing alone (README item 2; schema.js:443-450). The tie is gone from the end state, and the journal is the only source.
   - The order inside a tie is the `score_id` order (raceTieScoring.ts:47-49). It is irrelevant for points but becomes the `tied` chaining order.

7. **Settings changes over time.**
   - Case A: every `updateEvent` diff is journalled.
   - Case B: only the current value. The locks make the current discard profile the one in force for every race of its series. But:
     - The assignment-mode and overflow locks exist only since 2026-10-30 (f21ba8a). Events from 10-27 to 10-30 may have a journalled mode change **after** qualifying started. Older events may have had one with no trace. The library **refuses** such a `settingsChanged`, so a faithful log of those events cannot be replayed.
     - The discard lock flags are sticky. They hold no information beyond "a race of that series was scored once".
     - `'standard'` and `custom 4/8/8` cannot be told apart (equivalent).
     - An unknown stored mode or policy was silently normalized. The original text is lost if it was ever invalid.
     - `rule43` and the oversize confirmation per final start are never stored (see above).

8. **Boat identity over time.** Boats and Sailors are not journalled, and `updateSailor` changes nat and sail globally. The current `Boats` row may not be the identity under which past heats were seeded. The journal's `context.sail` strings keep the old labels per change, but there is no record _that_ or _when_ the identity changed.

9. **Heat names.** Legacy names ("Heat A" = round 0, multi-letter bases "Heat AA1") have no library `HeatId`. Events with them cannot be expressed (UNVERIFIED whether any such databases still exist; the code keeps parsers for them in views.js:12-13 and FSH:46-47).

10. **Derived data mixed into stored data.**
    - `Scores.points` for non-finishers, RDG1/RDG2 and penalties is rewritten on every recompute. DNC rows for boats in no heat are inserted automatically (journalled under `readLeaderboard`).
    - Leaderboard and FinalLeaderboard are caches.
    - None of this belongs in a log. A rebuild must ignore these columns and rows, not import them.

**Bottom line.** For a case-A event, a faithful log can be rebuilt, with these gaps:

- who decided each leaderboard-entered DSQ (assumed protest);
- edits against A6.1 ripple inside one save;
- `rule43` and the oversize confirmation (inferable by replay);
- on-sheet DPI or RDG (needs an invented line);
- transfers (not expressible);
- identity edits.

For case B, only a _plausible_ log can be synthesized from the end state. It loses:

- the original sheets behind every protest or correction (partly recoverable from snapshots);
- the timing of corrections relative to round building;
- entry timing, removed boats, undo history and transfers.

It must be checked by replaying and comparing every stored heat (Heat_Boat) and score before it is trusted.
